## 不通過詳情

### E6 Console 有紅字錯誤（favicon 404）

- **網址**：6 個頁面狀態皆同，例如 `http://127.0.0.1:8090/site/index.html`
- **步驟**：以全新 Chrome profile 開啟頁面 → 監聽 `Log.entryAdded`／`Runtime.consoleAPICalled`／`Runtime.exceptionThrown` 約 1.8 秒
- **實際結果**：每個頁面都出現 1 筆紅色錯誤（其餘 console 訊息為 0）：
  ```
  Failed to load resource: the server responded with a status of 404 (File not found)
  http://127.0.0.1:8090/favicon.ico
  ```
  以 `Network.responseReceived` 交叉確認：`GET /favicon.ico → 404`。`site/` 內沒有任何 `<link rel="icon">`，這個請求是 Chrome 自動向伺服器根目錄要的；伺服器根目錄是 `bible-site/`，該處沒有 `favicon.ico`。
- **判定理由**：計劃 E6 要求「6 頁都沒有紅字錯誤」，客觀上每頁都有 1 筆紅字，故不通過。
- **影響**：只影響 Console 乾淨度，不影響畫面與功能。
- **建議修法（給 PM 決定，非 tester 改）**：在 4 個 HTML 的 `<head>` 加 `<link rel="icon" href="data:,">`（不會發出請求），或把 `favicon.ico` 放到伺服器根目錄 `bible-site/`。前者只動 `site/`，後者不動 `site/`。

### E7 畫面文字非全部繁體（資料層，不是 `site/` 程式問題）

- **網址**：`http://127.0.0.1:8090/site/chapter.html?ch=5`（及 7:26、12:36 等）
- **步驟**：逐頁取 `document.body.innerText`，用系統的 OpenCC（`libopencc` 1.1，`s2t.json`）逐字掃描簡體字形
- **實際結果**：
  - `<html lang="zh-Hant">`：6 個頁面狀態全部正確；字集 UTF-8；`<title>` 皆有值（`index`／`chapter`／`search` 為「馬可福音」，`card` 為「經文卡片」）。
  - 網站**介面文字**（34 條，如「目錄」「經文搜尋」「共 N 筆」「下載圖片」「發生錯誤，無法載入資料：」）經 OpenCC 掃描 **0 個簡體字**。
  - **經文內容**有 2 個簡體字形，共 9 處：
    | 字 | 繁體 | 次數 | 出現位置 |
    |---|---|---|---|
    | 脚 | 腳 | 8 | 5:4(×2)、5:22、6:11、7:25、9:45、9:46、12:36 |
    | 叙 | 敘 | 1 | 7:26「屬叙利非尼基族」 |
  - 這 9 處與 `.verify/mark.txt` **逐字相同**（`脚` 在來源檔也是 8 次、`叙` 同）；`mark.json` 的 CJK 字集是來源檔的子集，沒有網站自行插入的字。另有 12 個 OpenCC 會改寫、但屬異體／詞義用法的字（干、准、凶、唇、岳、斗、游、雇、困、愈、背、家、具），不算簡體，不列入。
- **判定理由**：計劃 E7 要求「全部繁體」，畫面實際有 9 處簡體字形，故不通過。
- **歸屬**：**不是 `site/` 的問題**，`site/` 依鐵則只顯示 `mark.json`；要修必須改 `.verify/mark.txt` 或 `build_data.py`（資料層），再重跑 `verify_text.py` 與 `check_all.py`。若 PM 認定 E7 的「全部繁體」只指介面文字，則本項可改判通過（介面 0 個簡體字）。
- **附註（標題）**：`chapter.html` 與 `search.html` 的 `<title>` 都是「馬可福音」，未帶章號／「搜尋」。不算錯誤，但可考慮改成「馬可福音 第 N 章」「經文搜尋」以利分頁辨識。

## 需人工詳情

### E2 深色模式外觀

- **原因**：headless Chrome 可以模擬 `prefers-color-scheme: dark` 並量到顏色與對比度，但「看起來是否清楚、順眼」是主觀判斷，程式無法代替真人。
- **已完成的客觀量測**（供 PM 複核，非猜測）：
  - 深色變數確實生效：6 個頁面狀態 `body` 背景皆 `rgb(23,22,20)`、前景 `rgb(233,230,220)`，與淺色（`rgb(247,245,239)`）明顯不同；已擷取 375px 深／淺色截圖各 5 張交叉確認。
  - WCAG 對比度（門檻 4.5:1）：本文 14.48、頁尾 6.85、`verse-num` 6.85、`ch-count` 6.17、導覽連結 13.05、**導覽 active 7.86**、按鈕 7.86、搜尋結果出處連結 7.08、`<mark>` 標示 19.56；**全部 ≥ 4.5，沒有不足的項目**。
- **需人工確認**：深色下的實際觀感（尤其 `<mark>` 仍是黃底黑字、按鈕為橘底深字，是否刺眼或看不清）。

### E4 鍵盤操作與焦點可見

- **原因**：headless Chrome 可以送出 Tab 並讀出 `document.activeElement` 與 computed style，但「焦點圈看不看得見、順不順」需真人目視。
- **已完成的客觀量測**：
  - Tab 可走遍所有可聚焦元素，沒有漏掉：目錄 21/21、第 1 章 5/5、第 12 章 6/6、第 16 章 5/5、搜尋 279/279、卡片 6/6。
  - 輸入框、按鈕、下拉：`outline: solid 2px rgb(179,84,0)`，明顯可見。
  - 搜尋結果出處連結：瀏覽器預設 `outline: auto 1px`，可見。
  - **導覽列連結與章節卡片：`outline: none`**，只靠背景色（`--border`）或 `box-shadow` 變化示意，這是 CSS `:focus { outline: none }` 造成的。
- **需人工確認**：導覽列與章節卡片只用背景／陰影變化，鍵盤使用者是否看得出來（這是本項最可能需要修的地方）。
